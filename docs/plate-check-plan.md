# Plate Check — product and data plan

Status: local web prototype built and browser result flow checked, revised 2026-10-22. Product priority: **speed from opening the live scanner to a highlighted plate, and from tapping that plate to a useful result**, ahead of API cost and implementation simplicity. Repository: `empirerecords`, branch `main`, base commit `01ac6c9`. Live NYC API queries and a narrow-browser lookup were completed. Physical phone scanner benchmarks and public traffic checks remain open.

## Product shape

Build a mobile-first page at `/plate-check/` in this static site. It should work in a phone browser and be installable to the home screen as a progressive web app. Build a native mobile scanner when measured web performance cannot deliver the tap-to-select experience; the website and app can share lookup and result logic.

Flow: open the rear camera to a **continuous live view**, highlight plausible plate text in the viewfinder, and let the user **tap the plate itself**. No shutter or photo-taking step. While the camera is open, the app may quietly look up a stable candidate after repeated agreeing reads. Tapping opens a result sheet immediately with the recognized plate and a visible, editable state. The default state is `AUTO`: it queries all states in NYC's chosen datasets. If one state appears, show its records; if the same plate text appears in more than one state, require the user to choose the state before showing a score. The user can enter a two-letter state up front to narrow the query. Reuse a fresh lookup only for an identical key or a complete `AUTO` result filtered to the chosen state. Pause scanning while the result sheet is open; resume when it closes. Manual entry remains a fallback when scanning is unavailable or wrong. Do not persist searched plates, video frames, location, or query history in the app. A no-match result means only that the selected sources returned no record.

The result can have the joke's punch: an **“asshole energy”** meter and a short line such as “Yep, this plate has a parking record.” Generate that copy from verified categories and counts with deterministic templates so it appears as soon as the data arrives. Label it as commentary on the plate's public record, never a factual claim about who currently drives the car. The result sheet should open immediately; the data-backed verdict can appear at once only if a valid prefetched lookup is ready.

The playful result should describe the **public record associated with a plate and state**, never identify the current driver or owner. A plate can be transferred or reused; a ticket can later be paid or dismissed; OCR can confuse characters; and enforcement is not uniform. Show the source, date, violation label, and data freshness next to any score. Avoid a shareable ranking or searchable history of plates.

Their collision and vehicle IDs are internal event keys. Do not claim a plate-to-crash match from these tables.

## Data and scoring rules to validate

1. Match the normalized plate **and** registration state exactly for a scored result. The scanner reads plate characters but does not claim to read the state. `AUTO` queries all states, including NJ, and only resolves a single unambiguous state automatically. Display every recognized character and the inferred or chosen state for correction. Plate type is not read by this prototype; a plate and state can still be reused across vehicles.
2. Query a bounded recent period, initially 24 months, and return aggregates plus a small number of source rows. Show the exact period and each dataset's update date. Avoid downloading entire datasets to a device.
3. Keep the public facts separate from an editorial score. A first scoring draft can weight school-zone speed and red-light camera records, moving summonses, bike-lane obstruction, hydrant obstruction, and double parking more than meter or street-cleaning tickets. Do not assign final weights until violation labels and codes have been sampled and checked against NYC's code dictionary. Explain the final formula in the UI.
4. Do not present an unconfirmed scan as a definitive score; a provisional result can appear immediately. Show partial results clearly when a source times out or is rate limited. A missing record must not become a positive character judgment.
5. Validate whether status and dismissal can be determined from each row before using that status in copy or scoring. Treat all records as **issued** unless the source explicitly supports a stronger claim.
6. For speed **and** accuracy, require agreement across several live reads before prefetching. At tap, compare the selected plate with the latest stable read, and run a more careful local check only when characters or state are uncertain. If those readings conflict, discard prefetched results and ask for a quick correction before showing a definitive verdict. Never attach cached records to a different plate or state.

## Architecture and latency

- The existing `nyc_open_data_mcp/server.py` provides `nyc_search_datasets`, `nyc_get_dataset_columns`, and `nyc_query_dataset` for discovery and research. It is a local, read-only MCP server, not a browser API or a production backend. The app should query known Socrata datasets directly or through a small server endpoint; it should never expose arbitrary SoQL to visitors.
- For an initial prototype, query the Socrata read-only HTTPS API concurrently from the browser and time each source. [Socrata documents browser CORS support](https://dev.socrata.com/docs/cors-and-jsonp.html). Anonymous traffic can be throttled; if a proxy with an app token, caching, or an indexed store is faster or needed for public traffic, use it. Verify the chosen API version's token requirements. [Socrata app-token guidance](https://dev.socrata.com/docs/app-tokens.html).
- Run text recognition **on the device as the camera streams**, keep only plausible plate candidates, and stabilize each candidate across successive frames before drawing a tap target. Process a bounded region and skip frames when the recognizer is busy; do not queue frames or call a cloud model for every frame. Text recognition alone may highlight plate-like signs or misread characters, so benchmark candidate accuracy and add a plate detector if needed.
- For an iOS app, [VisionKit `DataScannerViewController`](https://developer.apple.com/documentation/visionkit/datascannerviewcontroller) already provides live text highlighting and a tap callback; benchmark its `fast` and `balanced` settings on real plates. For Android, [ML Kit Text Recognition](https://developers.google.com/ml-kit/vision/text-recognition/v2/android) supports real-time camera frames and text boxes. The website can use [camera `getUserMedia`](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia) over HTTPS with a preloaded [Tesseract.js](https://github.com/naptha/tesseract.js/) worker as an initial prototype; its actual first-load time, recognition rate, and battery impact on phones are open measurements. A web page cannot assume access to the native VisionKit scanner.
- `gpt-6-luna` leaves the live scan path. Use it only as an optional second pass on a **selected, low-confidence** plate crop after a tap, and never delay opening the result sheet on it. A model is unnecessary for the verdict copy or the score. If this fallback is built, keep the API key on a server, disclose that a crop leaves the device, and measure whether it improves successful lookups enough to justify added latency. ChatGPT plan usage is not an application API budget; the [OpenAI API has per-token pricing](https://developers.openai.com/api/docs/pricing).
- Pricing snapshot for that optional fallback, 2026-10-22: [GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna) is $0.10 per million input tokens and $0.50 per million output tokens at Standard rates; Fast mode is 2× those rates. [GPT-5 nano](https://developers.openai.com/api/docs/models/gpt-5-nano) has lower nominal rates ($0.05/$0.40), but it is [deprecated with a December 11, 2026 shutdown](https://developers.openai.com/api/docs/deprecations). Image-token counts vary by model.
- For the fastest tap, speculatively query the plate-keyed NYC sources once a stable candidate has appeared in repeated reads. Deduplicate repeated reads, throttle new prefetches, and keep results only in short-lived memory. Do not query every frame. The UI explains that a candidate can be sent for lookup before a tap. On tap, reuse a response only for the identical normalized plate and state mode; otherwise query then. Render each completed source with freshness and partial-result state. [Socrata warns that abusive request volume can be throttled](https://dev.socrata.com/docs/app-tokens), so benchmark and rate-limit prefetch before public release.
- Target an immediate sheet transition (under 100 ms on a measured device) and a data-backed verdict within one second for a prefetched, stable plate; these are product goals, not measured performance claims. Time camera permission, recognizer initialization, time-to-highlight, candidate stability, prefetch completion, tap-to-sheet, and tap-to-data-backed-verdict separately. If Socrata lookup dominates, benchmark a dedicated indexed lookup service for the chosen datasets rather than claiming that direct API calls will meet the target.
- The Empire Records GitHub Pages site can host the website interface. A cloud fallback or tokenized Socrata proxy needs a separately hosted endpoint for secrets and request limits. With on-device scanning, no camera frames need to leave the device for the normal flow.
- Keep `/plate-check/` buildless like the rest of Empire Records. Add a portfolio link only after the page has been tested. GitHub Pages can serve the static interface; a later proxy, if needed, must be hosted separately.

## Build sequence

1. Completed a live data spike for the three used datasets: exact SoQL queries, NJ rows, CORS, update dates, and response times were observed on 2026-10-22. The optional fiscal-year issuance dataset has not been integrated.
2. Built the static `/plate-check/` PWA with local Tesseract.js live OCR, tap targets, immediate result sheet, `AUTO`/two-letter state control, throttled prefetch, parallel NYC queries, source cards, error states, and a deterministic score. The UI never stores plate records or frames in the service worker.
3. Ran `node --test plate-check/data.test.mjs` (five passing tests). A narrow in-app browser manual lookup of a real NJ plate resolved `AUTO` to NJ and showed source-linked rows with no console errors. Desktop layout geometry showed no horizontal overflow. This is not a physical phone camera test.
4. OCR check, 2026-10-22: the whole-frame `SPARSE_TEXT` scanner read 0 of 5 synthetic plates correctly. A user-framed crop read with `SINGLE_BLOCK` gave 4 of 5 (see `plate-check/README.md`). Tesseract was replaced by the fast-plate-ocr `cct_xs_v2_global` ONNX model, tested on OpenALPR's 222 real US plate photos: about 90% correct in daylight and dusk, about 5% wrong opens, 47% correct in heavy-noise night. See `plate-check/README.md`.
5. Next: test live recognition and tap boxes on iOS Safari and Android Chrome; measure warm-up, time to highlight, prefetch cost, false positives, and tap-to-verdict. Build native VisionKit/ML Kit scanners only if the website misses the measured experience target.
6. Before wider promotion, verify anonymous API limits, source freshness and scoring language under real traffic. A tokenized proxy, if needed, must keep secrets on the server.

## Source and repository notes

NYC says its open datasets are informational and may be incomplete or corrected: [NYC Open Data Terms of Use](https://data.cityofnewyork.us/stories/s/Terms-of-Use/k9k7-3cje). The MCP server's reported `row_count` in catalog search currently comes from page views, and its schema tool labels `rowsUpdatedAt` as `row_count`; do not use those values as record totals for the app. Its 429 text mentions an `APP_TOKEN` variable that the server does not actually send.
